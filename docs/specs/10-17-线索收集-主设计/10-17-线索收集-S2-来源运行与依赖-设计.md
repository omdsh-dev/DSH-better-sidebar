**状态**：待用户批准

## 1. 目标与边界

为来源提供一致的 HTTP、CLI、DSH 内 MCP 运行边界，以及可由统一设置页消费的 CLI 依赖、安装和授权能力。不是新建通用系统包管理器，也不是把任意模型给出的命令当作来源。

内置 GitHub 使用 gh，飞书使用 lark-cli。每个来源只实现自己需要的通路，不要求三种运输重复实现，不在失败时隐式换成另一套 HTTP 身份。

本 Spec 拥有依赖／安装／连接状态契约及运行时，具体 CLI 资源命令由 S3、S4 拥有，设置页面由 S8 拥有。

## 2. 注册与共享对象

来源描述符通过可选 `dependencyIds` 数组及可选 `connectionId` 引用独立注册的依赖和连接。依赖及连接定义由本 Spec 的运行时管理，来源数据模型由 S1 管理；这些标识不重复定义 CLI 或凭据。CLI 依赖与来源不是一对一：Issues／PRs 共用 gh；飞书文档／任务共用 lark-cli 和同一授权连接。

依赖定义由受信的已安装来源插件注册，包含：

- 稳定 dependencyId、显示名称、命令名、兼容版本要求和已验证的推荐安装版本。
- 不访问账户的可执行文件／版本探测能力。
- 支持的平台与架构；手动配置路径的能力。
- 可选的安装计划与执行能力，及没有自动安装方式时的官方手动指引。

连接定义包含凭据归属、非秘密配置、授权状态、显式连接／取消入口，以及来源所需的能力说明。核心不替每个平台发明 OAuth 协议。

公开操作至少覆盖依赖 inspect、安装 plan/start/status/cancel、连接 status/connect/cancel。这些是人操作的宿主服务／已认证 UI 路由，不注册成 Agent 工具。具体路由组织沿用插件现有 API 风格，不新建第二套 RPC 框架。

## 3. 三类运行边界

### HTTP

由来源宿主代码发出请求，继承宿主代理行为；请求具备取消、超时、分页和明确错误。需要自有秘密时按每次操作从 `ctx.credentials` 解析，不复制到客户端偏好、模型、线索数据或导出包。

请求的目标主机与连接配置一致，不能把 Authorization 盲目转发到另一主机的重定向或资源链接。来源负责解析业务响应；核心只归一化可见状态，不向模型透传原始请求／响应头和诊断正文。

### CLI

可执行路径来自依赖解析，参数采用 argv 数组，不拼接 shell。内容通过结构化参数或 stdin 传递；避免把大正文放进命令行。受控环境继承必要的用户运行环境，但不把 DSH 自身凭据和无关秘密成批交给子进程。

每个资源操作具备取消、超时、输出边界和退出码处理；JSON 解析失败不能冒充空列表，非零退出不能按成功处理。对输出过大的结果明确分页／限制，不能静默吞掉后半段。

安装使用的路径不依赖当前会话 cwd。来源操作所需 cwd 由操作语义明确传入，不能因为用户切工作目录而找到另一份 CLI 配置或执行文件。

### DSH 内 MCP

只对接已经由 DSH 配置并注册的 MCP 能力。来源插件声明业务操作到宿主工具／资源的映射，复用宿主 MCP 连接与鉴权，不创建隐形第二个 MCP 客户端，不代装或改写 DSH 的 MCP profile。

调用必须经过宿主公开执行路径及其 guard／审批机制，正确传递取消信号和存在的调用主体。Agent 调用不得丢掉其会话上下文；UI 调用不得伪造一个 Agent、打开隐藏 turn 或绕过审批。

若宿主某条执行路径只能在活动 Agent turn 中审批，闲置 UI 请求应返回明确的 operation-unavailable／approval-required 状态，不暗中降级为无审批调用。来源只声明实际可用的编辑能力。用可运行的 MCP 夹具证明无审批读取可用、受限请求明确失败，而不是仅声明一个 transport 枚举即算支持。

## 4. 凭据与授权责任

| 接入 | 凭据拥有者 |
|---|---|
| 自有 HTTP 来源 | 宿主 `ctx.credentials` 或来源明确声明的宿主授权服务 |
| gh 来源 | gh 自己的登录与凭据存储 |
| lark-cli 来源 | lark-cli 自己的应用配置、登录与续期 |
| DSH 内 MCP 来源 | 宿主已配置的 MCP 连接 |

统一的是访问 API、状态和 UI，不强行搬运第三方 CLI token 到 `ctx.credentials`。不调用输出 token 的命令来“导入登录态”。配置页可显示账号／连接摘要和权限不足状态，不显示实际秘密值。

本期保证插件的数据流不主动泄露凭据，不承诺隔离同 OS 用户的工具进程，也不隔离同进程受信插件。不得自动把 Keychain 等存储降级为普通文件。

授权只能由用户显式点击连接／重新授权发起。人可见的授权 URL、验证码与二维码经来源声明的人工通路展示；机器轮询句柄、refresh/access token 和原始配置不得进入 Agent 上下文或原样日志。授权 URL 视为不透明字符串，不随意重编码。CLI 返回哪些字段可给人，由适配器白名单投影，而不是转发整份 stdout。

CLI 存在、已安装、版本兼容，不等于已授权。授权状态可在正常资源请求时更新；默认不做周期性的 auth status --verify、dry-run 或“健康检查”。`--dry-run` 不是只读保证，不能用于依赖发现或自动认证探测。

## 5. CLI 发现与版本

解析优先级：用户显式指定的路径；插件当前选用的托管版本；兼容的 PATH 命令。路径配置错误须明确报错，不能静默绕过用户显式路径使用另一个账号环境。

依赖状态区分 unknown、missing、incompatible、ready、installing、failed。连接状态独立表达两步配置：`configuration` 为 unknown／missing／ready／not-required；`authorization` 为 unknown／not-authorized／authorizing／ready／expired／denied／scope-insufficient。缺少应用配置时提供配置动作；配置就绪但未授权时提供连接动作；无需应用配置的来源使用 not-required。过期、拒绝与 scope 不足必须分别呈现；仅配置完成或安装成功不能显示已登录。S3/S4 的来源适配器报告这些状态及适用的人工动作，S8 不依据自由文本猜下一步。

版本探测仅使用已确认不会访问账户的方式，不调用业务命令。各内置来源必须记录实测兼容版本及探测契约；推荐安装版本必须固定，不能浮动指向 latest。具体发布版本由实现时的实际兼容性验证确定并随来源发布，不在设计阶段把未验证版本冒称支持。

同依赖的发现、安装任务与状态在插件内共享，多个 Tab／设置页只订阅同一个结果。安装结束使相关检测失效并重新探测，无需重启 DSH。

## 6. 一键安装契约

### 6.1 计划与人工确认

来源可提供安装能力；没有能力或当前平台不支持时，保留手动安装指引和路径配置。内置 gh、lark-cli 在有官方受支持分发包的平台应提供一键安装。

安装计划必须先展示：CLI 名称、固定版本、平台／架构、分发来源、目标目录、是否有现成系统安装以及预计动作。执行使用用户确认的同一计划；计划失效或目标版本变化时重新确认，不能在确认后悄悄安装新版本。

来源安装策略允许演进，但只能来自已注册的受信来源代码。不得接受 Agent、线索内容或 .cluepack 携带的脚本／命令作为安装动作。无需另造可执行工作流 DSL。

### 6.2 安装位置与分发

默认安装根为 `$DSH_HOME/tools/<dependencyId>/<version>/`，未设置 DSH_HOME 时使用宿主认定的用户数据根。目标是插件托管的用户级副本：

- 不覆盖系统 CLI，不修改全局 PATH，不使用 sudo，不自动安装 brew／apt／winget 等系统包管理器。
- 优先官方预编译分发；如采用 npm 分发，只允许在托管目录中的局部安装，禁止全局安装或复用 DSH profile 的依赖目录。
- 下载／安装能力应验证官方分发的完整性；归档解压不能逃逸目标目录。来源拥有具体平台分发描述，不由核心猜发布资产名。
- 成功前使用独立暂存位置；下载、校验、解包或探测失败不能破坏之前可用的版本。
- 手动指定路径始终优先。若用户装了托管副本但显式路径仍指向别处，界面必须展示实际使用路径，允许显式切换，不能假报已经使用新版本。

插件自己的 npm manifest 不新增 preinstall/install/postinstall/prepare；安装只发生于运行时人工 action。第三方分发若内部执行安装步骤，必须包含在计划中，不是插件加载时的隐式副作用。

### 6.3 状态与取消

统一安装过程提供阶段、可用时的进度、结束结果和取消入口。没有总量就显示阶段性进度，不伪造百分比。取消传播到下载和子进程；只清理本次所属暂存资源，不删除用户手动路径或系统安装。

同一依赖同一安装目标只允许一份在飞任务，多视图共享进度。任务结束后重新检测真实可执行路径和版本，只有通过才显示 ready。失败可重试，保留可读的脱敏原因。

安装本身不触发应用创建、登录、auth refresh 或资源请求。安装完成后由用户另行发起连接。

## 7. 错误语义

来源运行至少映射 S1 的稳定错误类别。CLI 适配器解释自己的成功／失败信封，不能统一假设顶层 code===0。授权过期显示重新连接入口，不在资源读取失败后自动发起交互登录。

高风险写需要额外确认的 CLI 响应不得被当作网络重试并自动追加 --yes；应保留草稿、在 UI 展示真实动作摘要并取得显式确认后重试同一操作。Agent 不获得写入或安装接口。

依赖缺失只影响使用该依赖的来源，本地文件和其他已就绪来源继续可用。安装器不可用不能使整个 better-sidebar 插件被 Cordis 静态 inject 禁用。

## 8. 验收与测试

- 在隔离临时目录中使用假 CLI 验证 argv、stdin、取消、超时、输出界限、结构解析和错误归一化；测试不继承真实用户 CLI 配置、HOME 凭据或 Keychain。
- 检测与安装测试证明不会调用 auth、业务请求或 dry-run。真实授权仅在用户显式同意的独立验证中运行；不能拿真实账号作为 CI fixture。
- 覆盖缺失／不兼容、显式路径失败、托管版本与 PATH 并存、安装中重复点击、多视图共享、失败保旧、取消、损坏归档与路径穿越。
- 安装后真实探测成功才显示完成；不改 PATH、不写系统目录、不触发登录均有断言。
- 用本地 HTTP 和 MCP fixtures 验证读取、取消、秘密不回传以及宿主策略拒绝。不依赖公网账号证明运行框架。
- 跨平台选择、可执行路径和 ZIP／tar 分发处理按 Windows、macOS、Linux 实测支持矩阵声明；没有官方资产的平台显示手动配置，不声称自动安装成功。
- 完成情况严格区分夹具验证、真实 CLI 本地验证与第三方账号端到端验证。

## 9. 既有能力与集成

仓库已有 CLI 探测、确认对话框、上传进度和归档任务，但没有系统 CLI 安装器；插件包安装与 CLI 安装是不同职责。可以复用其局部模式，不能复用插件包安装脚本去覆盖用户系统工具。

运行时、依赖与安装契约由本 Spec 唯一拥有。S3/S4 注册各自依赖与授权适配，S8 展示这些状态与动作，S9 完成宿主入口集成。遵循 [仓库规则](../../../AGENTS.md) 和 [宿主契约](../../host-contracts.md)。
