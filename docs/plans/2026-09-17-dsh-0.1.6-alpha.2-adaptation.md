日期：2026-09-17　分支：`feat/tasks-graph-workflow-teams`（PR #680）

## 背景

用户实机（桌面 3384）已在 **DSH 0.1.6-alpha.1** 上运行，而插件此前钉的是 `0.1.5-rc.2`（`latest`/`next` 仍是 rc.2，`alpha` 线已到 **0.1.6-alpha.2**）。本次把插件的 **devDependencies 与 CI 挂载钉版**推到 `0.1.6-alpha.2`，**peer 下限保持 `^0.1.5-rc.1` 不动**——rc.2 用户不受影响，插件同时兼容两条线。

同时按要求核对了「rebase 上游」：插件仓库 `origin/main` tip `1fcf43ccbedd`（2026-09-11）**是当前分支的祖先**（13 ahead / 0 behind），git 层面无可 rebase 的内容；本文件记录的是 DSH 上游适配。

## CI 钉版为什么留在 rc.2（含证伪过程）

第一版把挂载车道也钉到 `0.1.6-alpha.2`，CI 的 `plugin-mount` **确定性失败**（重跑同样红）：`mount.e2e.ts:216` 等 `[data-dsh-better-sidebar] [title]`（插件底部工作台 tab 条）90s 不出现，`perf.e2e.ts:182` 同样卡在底部拖拽条。失败截图显示外壳正常但**没有活动会话**（会话面板停在空态占位），按 e2e 自己的注释「没有 session scope → 工作台没有 pane」推断：alpha 线在 CI 上不再自动激活 scratch profile 的种子会话。

关键一步是**证伪「这是本分支引入的」**：从 `origin/main` 拉探针分支 `probe/dsh-alpha2-ci-pin`，**只改这一行钉版**（零插件改动），用 `gh workflow_dispatch --ref` 触发（ci.yml 的 push 只对 main 生效，探针分支没有 PR 就不会自动跑）——`plugin-mount` **同样红**、同一断言、同一处（run `35484961070`）。本地（macOS）同一钉版 `pnpm test:mount` 却 7/7，说明这是 **alpha 线 + Linux CI 车道**的组合问题，与插件代码无关。

按仓库硬约束（不改 DSH 源码）与 KISS，处置是：**devDeps 继续跟 alpha.2（对齐维护者实机），车道回到已发布的 rc.2**，并在 ci.yml 注释与 AGENTS.md §2/§3 写明证据与「车道学会在 alpha 线激活种子会话之前，alpha 只做本地验证」。把车道适配 alpha 线（例如断言前显式点击种子会话，或等外壳自动选中）留作**独立事项**：那是 e2e 基础设施改动，不该混进依赖钉版推进。

## 不做 / 留待发版决定

- **不改 peer 下限**（用户确认）：`^0.1.5-rc.1` 继续容纳 rc.1/rc.2 用户；本适配对他们是无感的。
- **不改 README 的版本徽章与安装策略文案**：它们描述的是**已发布**的 v0.19.1（"已在 0.1.5-rc.2 上验证"），把分支上的 alpha.2 验证写进去会让已发布版声称未做过的验证。发版时（若该分支进入某个 alpha 版本）再一并更新。
- **不清理 `sideChatConnReconnect`**：跨线 shim 仍在用它（rc 线必需），删它要动 20 份词典且会让 rc 用户少文案。
- **源码编译需要 alpha.2 的类型**：标签对象里 `noExitCode` 在 rc 线类型上不存在（多余属性会被 TS 拒绝），所以本分支的 `pnpm typecheck` 以 alpha.2 为准；运行时两线都安全（多余键被忽略）。
